## 1. What this project is

A **D&D 5e (2024 / XPHB rules) character builder** - a React + Vite single-page
app. It reads 5e.tools content (fetched at runtime, cached offline in IndexedDB),
lets the user build a character through guided choices, and derives a live sheet
(abilities, HP, saves, proficiencies, features, spells).

**North star:** a Foundry-VTT-exportable digital sheet, **mobile-first but strongly
desktop-compatible**, running **entirely on the user's machine**, with a creation
**wizard** and an on-the-go **play mode** for in-person tables, with **no
distribution licensing problems** (ship code only; never bundle game data).

Successor to an earlier project at `C:\Sync\Projects\dnd-sheet` (no Foundry export
exists there).

## 3. Orientation

### Codebase shape

- `src/engine/` - **pure** rules engine (no network/DOM). Abilities, HP, saves,
  proficiencies, choices, prerequisites, class/subclass/species parsing,
  multiclass, optional features, feature effects, Foundry export/import. Heavily
  unit-tested (`*.test.js`, Vitest).
- `src/data/` - fetch, cache (IndexedDB), character repo, provider.
- `src/components/`, `src/pages/`, `src/selector/` - UI (builder tabs, selector
  panels, choice rendering, wizard, tutorial).
- `scripts/` - the Phase T harness and the code generators (see §7).

**Choice model:** user picks live in a recursive per-source "choice bag"
(`{ [choiceId]: { kind, picks[], sub? } }`); the engine derives everything from the
character's decisions. `deriveFromDb(character, db)` is the top derivation entry
point; `ownedFromDb` computes what the sheet already has (for dedup).

### Commands

```
npm run dev · test · lint · build
npm run sweep          # Phase T Tier 0, whole matrix (-- --strict, --class=X, --species=Y, --emit-actors)
npm run t2             # export oracle: re-export the 48 official premades and diff
npm run check:keys     # curated species-keyed registries vs the resolved catalog
npm run pdf:preview    # render the PDF sheet without the browser
npm run gen:uuids · gen:sources · gen:srd    # regenerate the committed SRD-derived registries
```

### Reference material

**The reference source material lives INSIDE the project**, at `DnD Source
Material/` (project root), and always will, on every machine. Resolve it as
`./DnD Source Material` and rely on it being there. It is **git-ignored** (never
committed or redistributed). **Read `DnD Source Material/README.md` first** - it
documents all four subfolders, their licences and what each is good for.

- `5etools Source Code` - 5e.tools source + **data** (`data/class/class-*.json`,
  `data/spells/`). The authoritative content the app consumes.
- `DnD 5e System Source Code` - the Foundry **dnd5e system** (DataModels in
  `module/data/`, SRD packs in `packs/_source/`). The **authoritative target
  schema** for the export, and the source of the generated registries.
- `Plutonium Module Code` - the 5etools to Foundry importer. `js/` is minified;
  usable as a mapping reference via search only. **Never bundled or fetched.**
- `Character Sheets in JSON` - real Foundry dnd5e actor exports. `Standard Premade
  Characters/` (48 files) = schema ground truth and the `npm run t2` oracle;
  `Plutonium Made Player Characters/` = the user's players (homebrew, NOT ground
  truth).

## 5. Foundry data model (reference)

How import and derivation work on the target side. Investigated from the real
exports plus the dnd5e system.

**A Foundry actor is a bundle of documents, not a computed sheet.** It holds an
`Actor` (base values + references) plus embedded `items[]` (class, subclass, race,
background, feat, spell, weapon, equipment). Almost nothing is a final number.

**Two interpreters run, at two different times:**

1. **Advancement system, at import / level-up (unfolds the recipe).**
   Class/subclass/race/background items carry an `advancement[]` array of typed
   steps: `HitPoints`, `Trait` (proficiency grants), `ItemGrant` (auto-grant
   feature items per level), `AbilityScoreImprovement`, `ItemChoice`, `Subclass`,
   `ScaleValue` (level to number tables). Foundry runs these to grant HP, create
   items, apply proficiencies and prompt for choices. One-time.
2. **Active Effects + calculators, at runtime (every sheet load).** Each item can
   carry `effects[]`, each with `changes: [{key, mode, value}]` where `key` is a
   data path (`system.attributes.ac.bonus`, `system.traits.dr.value`,
   `flags.dnd5e.*`) and `mode` is 2=ADD, 5=OVERRIDE, 4=UPGRADE, 3=DOWNGRADE,
   1=MULTIPLY. Then the system derives modifiers, save/skill totals, passive
   perception, AC, spell DC, HP max.

**What is stored vs derived.** Stored: Active-Effect changes, ScaleValue tables,
and **activity** configs on items. Even these lean on derivation: a weapon attack
carries `ability:""` + `damage.parts:[]` + `includeBase:true` and Foundry computes
hit/damage; a spell save uses `dc.calculation:"spellcasting"`. Custom bonuses are
stored only when they deviate from the default. **Never stored:** ability
modifiers, save/skill totals, AC total, spell DC, HP max, passive scores.

**Where the mechanics live.** 5etools content is prose. The **`foundry-*.json`
overlay** (in the MIT 5e.tools repo, fetchable from our mirror - see DDL-0009)
supplies the Foundry-specific mechanics prose cannot express, keyed by name+source.
We use a hybrid: **generated skeleton + curated overlay**, with the precedence in
§6.

## 6. Rules that keep being relearned

Distilled from the 82 decision entries. Several of these were learned three or four
separate times before being written down; that is why they are here rather than
buried in an entry.

### 6.1 How to investigate

- **Measure the premise before you fix it.** Half of a bug report routinely fails
  to survive opening the source. TC-0062's statement was half wrong; a "fix" to a
  hooks-order warning restored nothing because there was no bug.
- **Scan by PROSE, not by tag, and never filter by source first.** A signature that
  depends on editorial markup measures the marker, not the rule. Filtering
  resistances by `{@variantrule Resistance}` saw 37 features; matching the text saw
  96, and 11 reachable subclasses were silently broken. "Current source" is
  meaningless for subclass features - every legacy stub is reachable through the
  2024 chassis.
- **A derived signature must be NARROW, and you test it against both sides:** what
  must match and what must **not**. A bare `- dr:` anywhere in the YAML swept in the
  Dwarf; any `ItemChoice` swept in the Human. Both would have corrupted a curated
  lineage.
- **Before registering the case that appeared, sweep the dataset for its family.**
  One Lizardfolk symptom was five missing natural-armour species; one Druidic
  symptom was six prose grants. Without the sweep you fix 1 of 6, or invent 30.
- **Count how many real documents use a form before assuming it.** A comment
  asserting "this is the shape real premades use" was wrong: of the 48 sheets, zero
  used it and 12 used the other one, so the Human's Versatile feat was lost on
  every import.
- **Verify the probe's own assumption before reporting.** Several "bugs" a probe
  accused were defects of the instrument. Correct the instrument: 26 false
  positives hide the real absences the oracle exists to show.
- **Never write "engine-verified" without having run something.** Either run a
  probe, or the note says "inferred from the pattern".
- **HMR artifacts survive `location.reload()`.** With the React Compiler the module
  graph outlives a reload. **Open a NEW TAB** before treating a hooks-order warning
  as a bug.
- **A disposable probe over `autoBuild` plus an oracle** (the book, or what the data
  declares) certifies a whole family's derivation in minutes. Save the live pass for
  what needs eyes: art, layout, flow.

### 6.2 Data, sources and licensing

- **Ship code, never game data.** All content is fetched client-side from the public
  5e.tools mirror and cached; nothing is bundled or committed. Attribute SRD/CC and
  MIT (5e.tools) where applicable. **Plutonium is UNLICENSED**: private reference
  only, never bundled or fetched.
- **The SRD is REFERENCE, not authority.** Where it is only convention, converging
  is optional; where following it would penalise the user or the exported sheet,
  **diverge**. (The SRD grants "Unarmed Strike" only to Barbarian and Monk; a Wizard
  who lost their staff would reach Foundry with no attack button at all.)
- **A divergence that is not NAMED inflates the scoreboard.** Every deliberate
  divergence needs **two** things: a FORM that cannot be mistaken for the SRD's (its
  own advancement title, its own flag) **and** an `EXPECTED` entry in the comparator
  with the reason written down. Without both it contaminates the oracle. And before
  naming something expected, check the predicate is not swallowing a real gap.
- **Generate a registry from the SRD instead of curating by hand** whenever the fact
  is not derivable from 5etools (which item type an item is, resource pools, subclass
  identifiers, container capacity). Four registries already work this way; a new one
  is a script, not a list. **Precedence: curated -> SRD -> overlay.** The curated
  entry is the override; the SRD is the target system's own data; the overlay is
  third-party and matches edition-strictly.
- **Verify a data path returns 200 before adding it to the manifest.** One 404
  breaks the whole `Promise.all`.
- **Check the enum vocabulary in dnd5e's `module/config.mjs` before exporting a
  value.** Passing a 5etools code raw is the standard trap (`'1/2'` is not a
  spellcasting progression).
- **Upstream data can be wrong**, but a correction needs proof: incoherent with the
  entry's **own prose** and, where possible, cross-checked against the dnd5e SRD.
  `KNOWN_DATA_FIXES` is the only place for it. Never "correct" by memory of the book.
- **Resolve `_copy` on the DERIVATION path, not just in the selector.** Sixteen
  races and every legacy subclass stub inherit through it; reading the raw db gave
  speed 0 and dropped every domain spell.

### 6.3 Architecture invariants

- **The character stores DECISIONS; the pure engine derives everything else.** No
  computed state in the schema. `deriveFromDb` is the single entry point.
- **Foundry is the ONLY interchange format**, both directions.
- **Native where Foundry has a slot; `flags.builder5e.*` where it does not.** The
  flag wins on re-import; flag-less actors (premades, Plutonium) take the native
  path. A **new choice kind must be given a home** or it silently stops
  round-tripping.
- **Every player-decision field must appear in `decisionSummary`**, or the
  round-trip oracle is blind to it. The character's money sat at zero for months
  because of exactly this.
- **Prefer an additive field to a schema bump.** `unassignedSpells` and `container`
  both shipped with no migration: an old character has an empty bucket and derives
  identically.
- **Read an EXTERNAL actor by the marks it leaves, not by the form our export
  uses.** A foreign document writes whatever title it likes, so route a Trait by the
  **prefix of the chosen key**, never by its title; infer a lineage from its
  mechanical fingerprint, not its name.
- **The derivation decides state, not just the UI.** Equipping, being stowed,
  being prepared: the UI flow and the derivation must both enforce it, because an
  imported actor can arrive in a combination the UI cannot produce.
- **A choke-point component derives what it needs** (memoized and gated), rather
  than seven call sites plumbing a prop. Plumb by prop only when there is a clear
  owner of the data. `ChoiceList` and `SelectorPanel` are the choke points; a
  feature added there reaches every tab and wizard step for free.
- **Content the model cannot explain is CARGO, not garbage.** Losing content is
  bad; losing it **silently** is unacceptable. Keep it, warn, and re-emit it.

### 6.4 Product and UX

- **Freedom with a warning, never a hard block.** A convenience narrowing is a
  **pre-marked, removable filter**; a possibly-unwanted act is a **confirmation
  that states the reason**. Hard-hiding is only for an unambiguous rule (deduping
  the same origin). Over-limit renders in red; it is never hidden.
- **A filter option that reaches nothing is DISABLED; one that can never reach
  anything is REMOVED.** The base for "disabled" ignores the option's own filter;
  the base for "removed" is the raw catalog, never the screen (a pre-marked filter
  must not make its own options vanish). A removed-but-live combination in dev is
  the signature of a typo'd value: warn.
- **Text comes from the data, never authored by us.** Build a variant's prose from
  the official template and swap the tags. **Without the template, generate
  nothing** - better to not offer the lineage than to offer it mute.
- **Redundancy on the sheet can be FUNCTION, not noise.** Prose traits that repeat
  a meta chip often carry the correct working of the feature (the flight limit by
  armour weight is in the text, not the chip). Do not hide either one.
- **In-app dialogs only.** `confirm`/`alert`/`ask` from `components/common/dialog.js`
  on the shared dialog stack; never `window.confirm`.

## 7. Where to add what

The deliberate curation points. If you are about to hardcode a name in a component,
one of these is probably the right home instead.

| You have | Goes in |
|---|---|
| a subclass granting proficiency/language/save/resistance in prose | `engine/subclassGrants.js` (fixed: `SUBCLASS_GRANTS`; choices: `SUBCLASS_FEATURE_GRANTS`) |
| a **class** feature granting something in prose | `engine/classFeatureGrants.js` |
| a feature raising max HP | `engine/hpBonuses.js` |
| a feature adding a flat AC bonus | `AC_BONUS_FEATURES` (`engine/featureEffects.js`) |
| a class/subclass with its own AC formula | `UNARMORED_DEFENSE` (`engine/armorClass.js`) |
| a species with natural armour | `engine/naturalArmor.js` |
| a granted spell whose frequency only the prose states | `engine/grantedSpellUses.js` |
| a legacy sub-race coming back | `engine/legacySubraces.js` · `legacySwapLineages.js` · `legacyFiendishLegacies.js` (three forms; the rules are in DDL-0059/0060/0061/0063) |
| a scenario reprint folded into a mainstream species | `engine/mergedLineages.js` |
| a Foundry Active Effect or activity we must override | `engine/foundryEffects.js` · `foundryActivities.js` · `foundryFeatureUses.js` |
| a fact the SRD knows and 5etools does not | a generator: `npm run gen:uuids` / `gen:srd` / `gen:sources` |
| a deliberate difference from the premades | `DELIBERATE` (not looked at) or `EXPECTED` (looked at, with the reason) in `scripts/lib/premadeDiff.js` |

**`DELIBERATE` vs `EXPECTED`:** `DELIBERATE` means the comparator does not look
(document identity, prose, session state); `EXPECTED` means it looks, finds, and
knows why we are right. **Revisit a `DELIBERATE` entry whenever the decision it
protects changes** - removing `container` from that list exposed 55 real findings
that had been invisible for weeks.
